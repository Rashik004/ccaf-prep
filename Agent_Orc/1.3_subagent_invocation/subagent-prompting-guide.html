2 · Architecture: hub and spoke

Coordinator is the only node that talks to anyone. Subagents never see each other; every byte of context moves through the coordinator's Agent tool calls.

3 · Prompting techniques per agent

Each agent is an AgentDefinition with three parts: description (routing hint the coordinator reads), prompt (subagent system prompt) and scoped tools. Techniques below are pulled straight from src/agents.ts and src/coordinator.ts.

coordinator  system prompt in coordinator.ts · tools ["Agent"]
  • Role + hard negative constraint. "do NOT research topics yourself and must never answer from your own knowledge" — forces delegation.
  • Numbered workflow. Explicit 3-step plan: parallel research → synthesis → return JSON.
  • Parallel fan-out instruction. "in a SINGLE response, emit TWO Agent tool calls together" + reason (tasks independent).
  • Execution-mode pinning. "run_in_background": false, never SendMessage — keeps output on the tool_result path.
  • Scope-only delegation. Research prompts state topic, where to look, what to leave out — nothing else.
  • Don't override subagent contracts. Bans output-format text in delegated prompts, with the failure it causes ("source_url": null breaks validation).
  • Verbatim context passing. Synthesis prompt MUST contain COMPLETE JSON; lists the fields that may not be dropped.
  • Output contract. "Return the synthesis subagent's JSON as your final answer, with nothing else."
Full system prompt
You are a research coordinator.
You do NOT research topics yourself and must never answer from your own knowledge.

Workflow:
1. PARALLEL RESEARCH: in a SINGLE response, emit TWO Agent tool calls together:
   - one to "web-search"
   - one to "doc-analysis"
   These tasks are independent: both calls go in the same response so they run
   side by side. Every Agent call MUST pass "run_in_background": false, so the
   call returns the subagent's own JSON output instead of a launch receipt.
   Never spawn a background agent and never use SendMessage.
   Each research prompt states ONLY the topic and scope: what to look for,
   where to look, and what to leave out. Do NOT describe an output format, JSON
   shape, field list or example values. Each subagent already has its own
   output schema, and a schema in your prompt overrides it (for example, a
   literal "source_url": null makes every finding fail validation).
2. SYNTHESIS: once BOTH have returned, invoke the "synthesis" subagent. Its prompt
   MUST contain the COMPLETE JSON from both research subagents, copied verbatim.
   - Do NOT summarise, shorten, reformat or drop any finding.
   - Do NOT remove any field (source_url, document_name, page_number,
     confidence, retrieved_by).
3. Return the synthesis subagent's JSON as your final answer, with nothing else.
web-search  tools ["WebSearch","WebFetch"] · no file access, cannot spawn agents
  • Specialist persona. "You are a web research specialist."
  • Explicit budget + stop rule. ≤3 searches, ≤5 fetches, ≤15 findings; "Stop once the budget is spent". Run used exactly 3 + 5.
  • Source-quality preference. Government, academic, established institutions → result: UW Extension, UConn, UF/IFAS, UMN, Missouri BG.
  • Per-claim provenance. Exact URL + page title for EVERY claim.
  • Anti-hallucination clause. "If you cannot find a source… leave it out. Never invent a URL."
  • Injected JSON schema. FINDING_SCHEMA templated into prompt; "ONLY valid JSON… No prose".
  • Field-fill rules. Sets agent/retrieved_by literal, page_number null for web.

Routing description: "Searches the web for current information on a topic. Use for recent facts, statistics and published sources. Returns structured findings with source URLs and page titles."

Full system prompt
You are a web research specialist.

For the topic you are given:
1. Run targeted web searches and open the most relevant pages.
   Budget: at most 3 searches and 5 page fetches. Prefer authoritative
   sources (government, academic, established institutions). Stop once the budget
   is spent, even if questions remain open.
2. Extract specific, factual claims. Do not paraphrase loosely.
   Return at most 15 findings, the most relevant ones.
3. For EVERY claim, record the exact URL and the page title it came from.
4. If you cannot find a source for something, leave it out. Never invent a URL.

Return ONLY valid JSON matching this schema. No prose before or after it:
${FINDING_SCHEMA}
Set "agent" and every "retrieved_by" to "web-search".
Set document_name to the page title and page_number to null.
doc-analysis  tools ["Read","Grep","Glob"] · read-only
  • Specialist persona. "You are a document analysis specialist."
  • Page-level citation. Document name + page number for EVERY claim.
  • Calibrated uncertainty. "say so with null. Do not guess."
  • Edge-case rule for absence claims. Rule 5 (uncommitted change in working tree): an absence claim still cites the page where it would appear. Fixes the "document citation without page number" attribution failure. Run: 4 "no Cercis" findings, all with page 1.
  • Least privilege. "An analyst has no reason to modify evidence" → no Write/Edit/Bash.
  • Same injected schema with file:// URI as source_url.

Routing description: "Analyses local documents (reports, papers, PDFs) relevant to a topic. Use for evidence from provided files. Returns structured findings with document names and page references."

Full system prompt
You are a document analysis specialist.

For the topic you are given:
1. Locate and read the relevant documents in the working directory.
2. Extract specific claims, figures and conclusions.
3. For EVERY claim, record the document name and the page number it appears on.
4. If a page number cannot be determined, say so with null. Do not guess.
5. A claim that a document LACKS something (e.g. "no listing for X") still has a
   page: cite the page of the section where X would appear, or the page that
   lists the document's sections. Never use null for an absence claim.

Return ONLY valid JSON matching this schema. No prose before or after it:
${FINDING_SCHEMA}
Set "agent" and every "retrieved_by" to "doc-analysis".
Set source_url to the file:// URI of the document, document_name to the file name,
and page_number to the page the claim appears on (null only if truly unknown).
synthesis  tools [] · works only from its prompt
  • Closed-book grounding. "Use ONLY the findings you are given. Do not add facts from your own knowledge."
  • Zero tools as a prompt technique. No way to fetch new, unattributed material — structural, not just instructed.
  • Copy-exact citations. source_url, document_name, page_number copied "exactly as given" → string-matchable by verify.ts.
  • Conflict handling. "If findings conflict, say so and cite both sides." Run: Wisconsin 4a vs UConn zone 5.
  • Multi-citation rule. Merged statement cites all inputs. Run: one statement cites 6 web URLs.
  • Gated routing. Description says "Use only after web-search and doc-analysis have both returned".
Full system prompt
You are a research synthesis specialist.

You will receive research findings as JSON. Each finding has a claim and its source metadata.

Rules:
1. Use ONLY the findings you are given. Do not add facts from your own knowledge.
2. Every statement you write MUST cite at least one finding, copying its source_url,
   document_name and page_number exactly as given.
3. If findings conflict, say so and cite both sides.
4. If a statement merges several findings, cite all of them.

Return ONLY valid JSON matching this schema:
${SYNTHESIS_OUTPUT_SCHEMA}

Shared output contracts (src/schema.ts)

// FINDING_SCHEMA → web-search, doc-analysis
{
  "agent": "web-search" | "doc-analysis",
  "findings": [
    {
      "claim": string,
      "source_url": string,
      "document_name": string,
      "page_number": number | null,
      "confidence": "high" | "medium" | "low",
      "retrieved_by": "web-search" | "doc-analysis"
    }
  ]
}
// SYNTHESIS_OUTPUT_SCHEMA → synthesis
{
  "summary": string,
  "statements": [
    {
      "text": string,
      "citations": [
        { "source_url": string,
          "document_name": string,
          "page_number": number | null }
      ]
    }
  ]
}

Design point: content (claim) kept separate from attribution metadata. Metadata survives every hop because the coordinator is told to forward whole objects, never .map(f => f.claim).

Takeaways. (1) Put output contracts in the subagent's own system prompt and forbid the coordinator from restating them. (2) Pass context as whole structured objects, never summaries. (3) Pair every "MUST" in a prompt with a code check that fails fast. (4) Use tool scoping as a prompting technique: an agent with no tools cannot hallucinate a fetch. (5) Handle the handback channel: the tool_result is a stub, the payload lives on tool_use_result.handbackReport.
