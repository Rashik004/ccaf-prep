Task Decomposition Strategies

The same 10-file repo reviewed two ways: one single-pass call over every file, then a fixed chain of one local pass per file followed by an integration pass over the per-file summaries.

1. Load the directory in a fixed order

src/load-directory.ts:30-47

export function loadDirectory(dir: string): SourceFile[] {
  logPassStart(`Step 1: load directory ${dir}`);
  // Plain name sort: the zero-padded prefixes (01_ ... 10_) make it the intended order.
  const names = readdirSync(dir).filter(isSource).sort();
  const files = names.map((name, i): SourceFile => {
    const path = join(dir, name);
    const text = readFileSync(path, "utf8");
    return { position: i + 1, name, path, lines: sourceLines(text).length, text };
  });
  files.forEach(logFileRead);

  if (files.length < MIN_FILES) {
    checkFailed("Step 1 (load directory)", `files>=${MIN_FILES}`, `found ${files.length} .ts/.js files in ${dir}`);
  }
  logCheck(`files>=${MIN_FILES}`);
  log.out(`   ${files.length} files to review`);
  return files;
}

What: Reads every .ts/.js file, sorts the names, gives each file a 1-based position, and logs one [i] <path> (<n> lines) line per file. With fewer than 10 files it throws; otherwise it logs CHECK files>=10.

Why: Attention dilution depends on position: in one long context, the files near the end get less attention. A fixed order lets the later steps compare files 1-3 with files 8-10. Below 10 files there is too little to dilute, so the comparison would mean nothing.

2. One rendering of the source for every pass

src/load-directory.ts:54-59

export function numbered(file: SourceFile): string {
  const body = sourceLines(file.text)
    .map((line, i) => `${String(i + 1).padStart(3)}│ ${line}`)
    .join("\n");
  return `=== FILE ${file.name} ===\n${body}`;
}

What: Turns a file into a === FILE name === header plus numbered lines ( 12│ code).

Why: The single pass and the local passes use the same rendering, so the only difference between them is how many files share one context. The line numbers let each finding cite a real line, which the answer key scores. The │ format is also what step 8 tests for to prove that no source reached the integration pass.

3. One reviewer contract, three output schemas

src/schemas.ts:14-20 · src/schemas.ts:90-101

export const REVIEWER_SYSTEM: string = [
  "You are a senior TypeScript reviewer.",
  "Report real bugs only: code that behaves wrongly at runtime, is unsafe, or breaks a caller.",
  "Do not report style, naming or missing comments.",
  "Each finding cites the exact line number from the numbered listing you were given.",
  "Severity is one of critical, high, medium, low.",
].join("\n");
export const LOCAL_PASS_SCHEMA: Record<string, unknown> = {
  type: "object",
  additionalProperties: false,
  required: ["file", "bug_count", "issues", "exports", "calls"],
  properties: {
    file: FILE_NAME,
    bug_count: BUG_COUNT,
    issues: ISSUES,
    exports: { type: "array", items: EXPORT_FACT, description: "Every exported function of this file." },
    calls: { type: "array", items: CALL_FACT, description: "Every call this file makes into another module of the repo." },
  },
};

What: All three passes get the same system prompt. The single-pass and local-pass schemas share the per-file shape {file, bug_count, issues[{line, severity, description}]}. The local schema adds exports (signature, behaviour) and calls (line, callee, arguments, expects). INTEGRATION_SCHEMA (schemas.ts:104-131) allows only data_flow, api_consistency and pattern_consistency issues.

Why: With the prompt and output shape the same, any difference between the two approaches comes from the context alone. The exports/calls facts are the handoff from stage 1 to stage 2: the integration pass reasons over them in place of the source.

5. The single pass: every file in one context

function singlePassRequest(files: SourceFile[]): string {
  const ask =
    `Review all ${files.length} files below. Return one entry per file, in the order given, ` +
    `even when a file has no bugs.`;
  return [ask, ...files.map(numbered)].join("\n\n");
}
  // The baseline is only fair if every file really is in the one context.
  const missing = files.filter((f) => !user.includes(`=== FILE ${f.name} ===`));
  if (missing.length > 0) {
    checkFailed("Step 2 (single-pass)", `single-pass request holds all ${files.length} files`, `missing ${missing.map((f) => f.name).join(", ")}`);
  }
  logCheck(`single-pass request holds all ${files.length} files`);
  // One call is what makes this the single-pass baseline.
  const count = callsTagged(TAG);
  if (count !== 1) {
    checkFailed("Step 2 (single-pass)", "single-pass calls==1", `made ${count} calls`);
  }
  logCheck("single-pass calls==1");

What: Joins every numbered file into one user turn. It checks that each === FILE header is present, makes the call, and checks that exactly one single-pass call happened. If the model leaves out a file, alignToFiles() gives that file an empty review instead of failing.

Why: This is the baseline the lesson warns against: every file competes for attention in the same context. A skipped file counts as dilution evidence, not as a program error.

6. Stage 1: one local pass per file, plus its interface

src/local-pass.ts:20-29 · src/local-pass.ts:39-52

function localPassRequest(file: SourceFile): string {
  return [
    `Review this one file.`,
    `Also describe its interface, for a later reviewer who will not see the source:`,
    `- exports: each exported function's signature and behaviour (units of the result, what happens when nothing is found).`,
    `- calls: each call into another module of the repo, with its line, callee, arguments as written, and what this caller expects back.`,
    "",
    numbered(file),
  ].join("\n");
}
  // Within stage 1 the calls are independent (no call reads another's output), so they
  // could run in parallel; they run one after another only to keep the log readable.
  // Stage 2 must wait for all of them: that dependency is what makes this a chain.
  for (const file of files) {
    const review = await reviewCall<LocalReview>(client, {
      model,
      tag: `local-pass file=${file.name}`,
      system: REVIEWER_SYSTEM,
      user: localPassRequest(file),
      schema: LOCAL_PASS_SCHEMA,
    });
    reviews.push(review);
    log.out(`   [${file.position}] ${file.name}: ${review.issues.length} findings`);
  }

What: Makes one call per file, each holding a single file, and asks for the bugs plus the file's exports and its calls into other modules.

Why: A file reviewed alone gets the model's full attention, so file 10 gets the same scrutiny as file 1. That is the structural fix for dilution. A local pass cannot see a bug that sits between two files, so it records the interface facts that stage 2 will need.

7. Guard the summaries before stage 2 trusts them

src/local-pass.ts:54-58 · src/local-pass.ts:88-95

  // Checked once every file is in, so the log holds all N results before any failure.

/** bug_count must equal the number of issues: a rule the JSON Schema cannot express. */
function checkBugCounts(reviews: LocalReview[]) {
  const wrong = reviews.find((r) => r.bug_count !== r.issues.length);
  if (wrong) {
    checkFailed("Step 3 (local passes)", "bug_count==issues.length", `${wrong.file}: bug_count=${wrong.bug_count}, issues=${wrong.issues.length}`);
  }
  logCheck("bug_count==issues.length");
}

What: checkSchemaValid() confirms that each summary has the LocalReview shape and names the right file (CHECK local-pass schema-valid N/N). checkBugCounts() confirms that bug_count equals issues.length.

Why: In a chain, each stage consumes the one before it. A wrong summary would mislead the integration pass without any error, so the run stops before stage 2 starts.

8. Stage 2 reads summaries, never source

src/integration-pass.ts:22-34 · src/integration-pass.ts:45-53

function integrationRequest(summaries: LocalReview[]): string {
  return [
    `Below are per-file summaries of a ${summaries.length}-file TypeScript repo, one per file,`,
    `each with its local findings, its exports and its calls into other modules. You do not have the source.`,
    `Report only issues that span two or more files, in three categories:`,
    `- data_flow: a value changes meaning on its way between files (units, null vs throw).`,
    `- api_consistency: a call does not match the signature or behaviour of the export it targets.`,
    `- pattern_consistency: the same job is done differently, or a bug is handled differently, across files.`,
    `Do not repeat a bug that sits inside one file.`,
    "",
    JSON.stringify(summaries, null, 2),
  ].join("\n");
}
  // The decomposition holds only if this pass works from summaries. One numbered source
  // line in the request would mean raw code leaked into the second stage.
  if (NUMBERED_LINE.test(user)) {
    checkFailed("Step 4 (integration pass)", "integration input=summaries", "request contains a numbered source line");
  }
  logCheck("integration input=summaries");
  // `files` is used only here, to measure how much smaller the input is. It is never sent.
  const sourceChars = files.reduce((n, f) => n + f.text.length, 0);
  log.out(`   input: ${user.length} chars of summaries vs ${sourceChars} chars of raw source`);

What: Builds the stage 2 request from the N JSON summaries and the three categories. It fails if any NUMBERED_LINE ( 12│ ) appears in the request, then logs the size of the summaries against the size of the source.

Why: The integration pass compares each call against the export it targets, which no local pass can do. Feeding it the raw source would bring dilution back. The size line makes the cost visible: in the cited run the summaries were larger than the source (see RESULT.md).

11. Depth by position: files 1-3 against the last three

src/compare.ts:44-54

export function depthLine(label: "single-pass" | "multi-pass", reviews: FileReview[]): string {
  const n = reviews.length;
  const early = average(reviews.slice(0, 3));
  const late = average(reviews.slice(Math.max(n - 3, 0)));
  const verdict = late < early ? "observed" : "not observed";
  const line =
    `depth ${label}: files 1-3 avg ${early.toFixed(1)}, files ${n - 2}-${n} avg ${late.toFixed(1)}` +
    ` — drop-off ${verdict}`;
  logObservation(line);
  return line;
}

What: Averages the findings per file over the first three and the last three files, and reports drop-off observed or not observed. It logs the result as OBSERVED and never throws.

Why: Dilution shows up as fewer findings for later files. The sample repo plants local bugs at both ends, so a drop reflects attention rather than where the bugs are. Because this is a model-quality outcome, a run that shows no drop is still a valid result.

12. Score against the planted bugs, not the totals

function caughtByMultiPass(seed: SeededIssue, local: LocalReview[], integration: CrossFileIssue[]): boolean {
  if (seed.kind === "local") return caught(seed, local);
  return caughtByIntegration(seed, integration) || caught(seed, local);
}
  // The integration pass's own contribution: bugs the single pass missed and only the summaries exposed.
  const onlyIntegration = SEEDED.filter(
    (s) => s.kind === "cross_file" && caughtByIntegration(s, integration) && !caught(s, single)
  );
  lines.push("  Cross-file issues found only by the integration pass:");
  if (onlyIntegration.length === 0) lines.push("    (none)");
  for (const s of onlyIntegration) lines.push(`    ${s.id} ${s.file}:${s.line} ${s.description}`);
  return lines.join("\n");

What: comparisonReport() prints the per-file counts for both approaches, the totals (multi-pass = local + cross-file), the spread, and the 9 seeded issues with a yes/no for each approach. A finding counts when it lands within 2 lines of a seed. A cross-file seed counts for the integration pass when one issue names both of its files (answer-key.ts:81-87).

Why: A long list of findings is not the same as the right list. The answer key, checked against the files before any paid call, turns "more findings" into "planted bugs found". The last list isolates what stage 2 alone added.

13. Identical code, same verdict?

src/dilution.ts:13-18 · src/answer-key.ts:29-37

function verdictLine(label: string, pattern: IdenticalPattern, reviews: FileReview[]): { text: string; artefact: boolean } {
  const verdicts = pattern.sites.map((site) => flaggedAt(site, reviews));
  const artefact = verdicts.some((v) => v !== verdicts[0]);
  const sites = pattern.sites.map((s, i) => `${s.file}:${s.line} ${verdicts[i] ? "flagged" : "approved"}`);
  return { text: `    ${label.padEnd(12)}${sites.join("; ")} -> ${artefact ? "ARTEFACT" : "consistent"}`, artefact };
}
export const IDENTICAL_PATTERNS: IdenticalPattern[] = [
  {
    pattern: "items.forEach(async (i) => { await save(i); });",
    sites: [
      { file: "02_product-repo.ts", line: 27 },
      { file: "10_sync-job.ts", line: 30 },
    ],
  },
];

What: For the byte-identical forEach(async) line in file 02 and file 10, it records whether each approach flagged or approved each site. It prints ARTEFACT when the two verdicts differ and consistent when they match, and logs the outcome as OBSERVED.

Why: Identical code deserves identical verdicts. A difference can come only from the file's position in the context: the lesson's "contradictory feedback" symptom of attention dilution. It is reported rather than asserted, because a strong model on small files may not show it.
