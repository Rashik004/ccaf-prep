# 1.6 Task Decomposition Strategies — drills

### Q1. Claims processing: pipeline or adaptive plan
Your team automates insurance claim intake. Every claim goes through the same work: extract the fields from the submitted form, validate them against the policy, apply the fraud-rule checks, then draft the decision letter. The input format is fixed, and auditors need to see each step's output for every claim. A colleague proposes letting the agent plan its own steps for each claim, since some claims are simpler than others. Which decomposition would most effectively fit this workflow?

- A. Dynamic adaptive decomposition: the agent builds a plan for each claim and revises it as it learns more about the claim.
- B. A fixed sequential pipeline (prompt chaining): one focused step per stage, each taking the previous step's output, with every step logged.
- C. A single prompt that performs all four stages at once and returns the decision letter, to cut the number of calls.
- D. A coordinator that decides at runtime which specialist subagents to invoke for each claim.

**Answer:** B
**Why:** "A fixed sequential pipeline (prompt chaining)" fits: the steps are known in advance, the input is structured, and auditors need per-step output, which a pipeline gives through consistent results and step-by-step logging. Dynamic decomposition (A) suits open-ended work of unknown scope, and here it would make cost and audit trails unpredictable for no gain. A single prompt (C) merges four concerns into one pass and loses the per-step record. A runtime coordinator (D) adds a decision layer to a sequence that never changes.
**Source:** Task Statement 1.6, "Selecting task decomposition patterns appropriate to the workflow: prompt chaining for predictable multi-aspect reviews, dynamic decomposition for open-ended investigation tasks"; RESULT.md study point "Pick the decomposition shape from how predictable the task is".

### Q2. Adding tests to a legacy codebase
You are asked to "add comprehensive tests" to a 200k-line legacy service that has no tests and little documentation. Nobody on the team knows which modules depend on which. How should the agent decompose this task?

- A. Run a fixed pipeline that visits every file in alphabetical order and generates unit tests for each function it finds.
- B. Load as much of the codebase as fits into one context window and generate the whole test suite in a single pass.
- C. Map the codebase structure first, identify the high-impact areas, then build a prioritised test plan that is revised as dependencies are discovered.
- D. Start with the smallest, simplest modules so that coverage rises quickly, then move to the larger ones.

**Answer:** C
**Why:** "Map the codebase structure first, identify the high-impact areas, then build a prioritised test plan that is revised as dependencies are discovered" is the exam guide's recipe for open-ended work: the scope is unknown, so the plan must adapt to what each step finds. A fixed alphabetical pipeline (A) ignores impact and cannot react when it discovers a dependency. One giant pass (B) suffers attention dilution and has no plan. Easiest-first (D) optimises a coverage number instead of risk.
**Source:** Task Statement 1.6, "Decomposing open-ended tasks (e.g., 'add comprehensive tests to a legacy codebase') by first mapping structure, identifying high-impact areas, then creating a prioritized plan that adapts as dependencies are discovered"; RESULT.md study point "Open-ended tasks follow a fixed recipe".

### Q3. The integration pass misses a cross-module bug
Your multi-pass code review runs one local pass per file, then an integration pass over the per-file results. Each local pass returns only its list of bugs. A release ships with a bug where `stock-service.ts` calls `getStock(warehouseId, sku)` but `warehouse-repo.ts` defines `getStock(sku, warehouseId)`. Neither local pass flagged it, and the integration pass did not either. What change would most effectively let the chain catch this class of issue?

- A. Have each local pass also record its file's interface in the summary: exported signatures, and each call into another module with its arguments and the result it expects.
- B. Give the integration pass the raw source of every file alongside the summaries, so that it can check the call sites itself.
- C. Raise the local passes' output budget and ask for more detailed bug descriptions.
- D. Run the integration pass first, then the per-file passes, so that the local passes know what to look for.

**Answer:** A
**Why:** "Have each local pass also record its file's interface in the summary" gives the integration pass the evidence it needs: the integration pass can only find what the summaries pass on to it, and a bugs-only summary drops the argument order. Feeding it all the raw source (B) brings back the attention dilution the split was meant to remove. More detailed bug text (C) does not help, because neither file holds a local bug. Reversing the order (D) leaves the integration pass with nothing to work from.
**Source:** Task Statement 1.6, "Splitting large code reviews into per-file local analysis passes plus a separate cross-file integration pass"; RESULT.md study point "Each local summary has to carry interface facts, not just bugs" (the 06 local pass recorded the swapped order at L1446-1451, and the integration pass reported it).

### Q4. An incident investigation that finds something unplanned
An agent investigates intermittent data corruption in a system the team does not know well. It follows a five-step plan written in advance: check application logs, check the database, check the cache, check the message queue, write a report. At step 2 it finds that only records written by a nightly batch job are corrupted, and that job is not in the plan. What is the most effective way for the agent to proceed?

- A. Finish the remaining three planned steps first, then start a second investigation into the batch job.
- B. Add the batch job as a permanent step 6 in the investigation pipeline for all future incidents.
- C. Spawn parallel subagents up front to inspect every component of the system, so that nothing is missed.
- D. Revise the plan using the new finding: generate subtasks that investigate the batch job, and drop or reorder the steps that no longer apply.

**Answer:** D
**Why:** "Revise the plan using the new finding" is the value of adaptive investigation: in open-ended work, each discovery should reshape the remaining subtasks. Finishing the stale plan (A) spends effort on steps the evidence has already made less relevant. A permanent step 6 (B) hard-codes one incident's cause into a fixed pipeline. Fanning out to every component (C) is costly and ignores the lead the agent just found.
**Source:** Task Statement 1.6, "The value of adaptive investigation plans that generate subtasks based on what is discovered at each step"; RESULT.md study point "Pick the decomposition shape from how predictable the task is".

### Q5. One prompt for a multi-aspect review
Your CI job reviews each pull request with one prompt that asks Claude to check security, performance, error handling and accessibility at once. Reviewers report that the output gives each aspect only a sentence or two, and that real problems in all four areas are often missed. The four aspects are the same for every PR. How should you restructure the review?

- A. Let the agent decide for each PR which aspects matter, and review only those.
- B. Chain the review into sequential steps, one focused prompt per aspect, then combine the results into one report.
- C. Keep the single prompt but add a detailed checklist for each of the four aspects.
- D. Run the single prompt three times and keep only the issues that appear in at least two runs.

**Answer:** B
**Why:** "Chain the review into sequential steps, one focused prompt per aspect" is prompt chaining for a predictable multi-aspect review: each step gives one concern its full attention, and the fixed set of aspects suits a fixed pipeline. Letting the agent pick aspects (A) applies dynamic decomposition where the scope is already known, so aspects may get skipped. A longer checklist (C) keeps every concern in one pass, so attention is still split four ways. Consensus voting (D) hides real issues that are caught only intermittently.
**Source:** Task Statement 1.6, "Prompt chaining patterns that break reviews into sequential steps" and "prompt chaining for predictable multi-aspect reviews"; exam-guide Sample Question 12 rationale on consensus voting.
